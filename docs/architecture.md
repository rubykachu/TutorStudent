# Architecture map

Read this first in a new session. Product rules and content model: `docs/spec.md`; UI tokens: `docs/design-system.md`; the learner every lesson is written for: `docs/learner.md`; working rules for agents: `.claude/rules/`. Commands: `README.md`.

## Data flow

```
content/**/lesson.json  (+ tips.json per lesson, subjects.json, glossary/, ids.lock.json, legacy-lessons.json)
   | pnpm content:check   zod schema + lint (src/content/lint) + ids + review-hash gate
   | pnpm content:emit    only published lessons (CONTENT_INCLUDE_DRAFT=1 adds drafts,
   v                      CONTENT_INCLUDE_FIXTURE=1 the test lesson)
public/content/index.json + <lessonId>.json + <lessonId>.tips.json   (gitignored, rebuilt by dev and build;
                                                                      the tips list only for a lesson with tips)
   | fetched by the client
   v
src/app (child screens) -> src/learn players -> src/exercises -> src/progress (Dexie)
```

`pnpm build` runs `content:check`, a production `content:emit`, `scripts/offline-manifest.ts` (the list of files the service worker stores), `next build`, `scripts/offline-worker.ts` (writes `public/sw.js`) and the bundle check; `pnpm dev` runs `content:emit` first. Schemas in `src/schema/content.ts` are the single source for types, `content:check` and generator prompts. Per-subject settings (colour, icon, language `vi|en`, rule flags) live only in `content/subjects.json`.

## App modules (`src/`)

- `app/(child)/` home, subjects, lessons, profiles; `app/parent/` PIN-gated report; `app/dev/` galleries of visuals, exercises and mascot (a 404 in production); `app/unlock/` where a device enters the family code once; `app/api/session/` turns a right code into the cookie; `app/api/sync/` reads and writes the synced progress docs.
- `schema/` zod schemas. `content/` loader, index, `check.ts`, `stats.ts`, `tips.ts` (a lesson's tips from its `tip` blocks and its `tips.json`), `lint/` rules.
- `exercises/` explanation shown after every answer (`explanation.ts` picks the authored `explain` or derives one from the solution visual and accepted answer; `explanation-panel.tsx`), the eight basic exercise types (`choice`, `numeric`, `fill-blank`, `match`, `order`, `tap-region`, `tap-text`, `manipulate`) and `open-ended` (a sequence of steps), `grade/`, 3-level hints, feedback.
- `visuals/` `registry.ts` maps `visualId` to a component with `interactive`, `regions` and validators; shared primitives in `shared/`; lesson visuals in `<subject>/<lesson>/`. Lessons that share drawing code keep it in a shared folder and list only their own pictures in their catalog: `shared/plane/` (figures, probes, drawing and piece boards) and `shared/quadrilaterals/` (the four shapes: figures, construction boards, validators, `from-spec`), used by the two parts of Bài 19.
- `components/blocks/` `block-view.tsx` (one renderer for every block), `tip-card.tsx` (a tip), `video-player.tsx` (a video plays straight through; captions under the picture on a phone). `app/(child)/lessons/[lessonId]/tips/` the lesson's "Mẹo hay" page (`learn/use-lesson-tips.ts` fetches its list).
- `learn/` section player, review player, overview, next-step logic. `srs/` FSRS scheduling and review selection.
- `progress/` Dexie store (IndexedDB, per browser; `sync/` carries it between devices), streak, parent report and PIN; `reset.ts` erases one child's progress of one lesson in one transaction (`LESSON_RESET_POLICY` classifies every table; the parent page's "Học lại bài này" sheet, `components/parent/reset-lesson-dialog.tsx`, calls it). A sticker is kept by a reset, so lesson state, subject progress and the continue target read section records only. `mascot/` owl and its lines. `music/` the songs a sticker's sheet can play (`songs.ts`, the one list) and the player hook, and the background music of the outer screens: `background-music.ts` (the controller: a shuffled playlist of `BACKGROUND_MUSIC_IDS` that never repeats a track twice in a row, crossfades, fades in 1 s and out 0.5 s, ducks under a celebration, falls silent while narration, a video or a song plays; Web Audio buffers on the shared context only, never a media element, so iOS shows no Now Playing controls) and `background-music-runner.tsx` (`BackgroundMusicRunner` in the child layout feeds it the device switch `BACKGROUND_MUSIC_KEY` and the child's sound switch, the first tap, the page going to the background, and DOM media playing; `OuterScreenMusic` is rendered by home, a subject's lessons, the lesson page's list of parts, the grade and profile pickers; learning screens, the overview and the parent page render none). `lib/` config, shared sounds (`sound.ts`, `sound-manifest.ts`), media URLs, formatting.
- Sound playback (`lib/sound.ts`) never holds a tap back: handlers call `playSound`/`playSequence`/`playMusic` without awaiting. Short clips are decoded once into `AudioBuffer`s (after the first tap, tap and button first, capped at `MAX_DECODED_BYTES`) and started through one shared `AudioContext`; songs and any clip that does not fit use one reused `<audio>` element fed from an in-memory blob; a hidden page stops every sound and suspends the context, and so does `IDLE_SUSPEND_MS` without any sound (the background music holds it awake with `keepAudioAwake` while it plays); the next tap resumes it. Rules for each sound: `docs/design-system.md` section 7 "Âm thanh".
- Media loading: a lesson video and the overview narration are fetched whole into memory (`lib/media-download.ts` streams the response and reports bytes against `Content-Length`; `lib/use-media-source.ts` owns the blob URL, revokes it and aborts on leaving) and played from the blob, so the child sees `components/media-loading.tsx` (owl or play button in a progress ring, "Đang tải… 45%") while the file downloads and again on every `waiting`/`stalled`, and "Thử lại" when the download fails (for the narration only after a tap). The narration downloads as the overview opens (`useNarration`); a tap plays at once when it is done, otherwise the percentage stays and it plays on arrival. iOS lets only the tapped element play after an await, so the tap itself calls `lib/play-from-tap.ts` `playFromTap`: a ready element plays inside the tap, an element without its file starts and stops a silent clip to unlock itself, the blob is swapped into that same element (never a new one) and played when it arrives; a refused `play()` shows the play button again with no error, and events of the silent clip are ignored (`ignoringSilentClip`). A file with no `Content-Length` is streamed by the element itself and the percentage is its buffered share of the duration. `video-player.tsx` starts the download on the tap (as the screen opens for the video on screen, `preload="auto"`, which includes a card's clip once the child opens it); `learn/upcoming-video.ts` picks the video of the next screen, which `video-preload.tsx` downloads unseen into a one-slot memory holder (`storePreloaded`/`takePreloaded`) that the next player takes, one video at a time, aborted when the screen is left. Videos are never stored: no Cache Storage, IndexedDB or service worker holds them. `lib/network-status.ts` is the one answer to "is the network there" for every player (the video player, the narration, the song button and `video-preload.tsx`): offline when `navigator.onLine` is false or a download just failed with a network error (a `TypeError`, which is how wifi without internet shows), forgotten on the `online` event, when the page is visible again, on a tap of the offline state and on a success. Offline the video says "Cần mạng để xem video", the narration "Cần mạng để nghe đọc bài" and the song button "Cần mạng để nghe nhạc", with no ring and no percentage, and the preload waits; a failure the server caused (a status) keeps "Thử lại".
- Overview narration: `learn/narration.tsx` (the player card, `useNarration`, and `NarrationMiniPlayer`, a slim bar fixed to the top with pause/play, progress and close once the card is less than half on screen), `learn/use-follow-reading.ts` (the page follows the highlighted word until the child wheels, touches, clicks or presses a scroll key outside the narration's controls; "Theo dõi lời đọc" shows when the word is off screen, and pressing play again also resumes). The mini-player publishes `--narration-mini-height` for `scroll-padding-top`, like the bottom bar's `--bottom-bar-height`.
- Short viewports: the `short:` variant (`max-height: 500px`, a phone held sideways) in `globals.css` makes `BottomBar` one compact row (its children share it, `data-bar-secondary` keeps its width) and `BigButton` 44px tall.
- `access/` the family-code gate: `code.ts` makes and checks family codes (`OWL` + 5-character family part + 8-character signature, Crockford base32; the signature is the first 40 bits of HMAC-SHA256(`FAMILY_CODE_SECRET`, family id), so a code is checked by signing its family id again and no list of codes exists; `scripts/family-code.ts` (`pnpm family:code`) prints codes with the same functions), `env.ts` reads `FAMILY_CODE_SECRET`, `SESSION_SECRET` (both at least 32 characters and different) and `FAMILY_CODES_REVOKED` (no secret outside production means no gate; production without a valid setup serves nothing), `gate.ts` decides per request (`src/proxy.ts` runs it before every page and file; unlocked devices carry the signed `tutor_family` cookie, others are sent to `/unlock`, or get 401 for files and API calls), `session.ts` signs and checks the cookie (it holds the family id and a keyed fingerprint of the family's code signature, so revoking the family or changing either secret cuts its devices; `resolveFamily` turns a cookie into its family id, the only source of a family id on the server), `hmac.ts` the HMAC-SHA256 helpers both use, `origin.ts` the same-origin check shared by both API routes, `rate-limit.ts` locks an address after repeated wrong codes. `GET /api/session` gives the cookie's family id and code, made again on the server, to the parent page (`src/components/parent/family-code-panel.tsx`). The manifest, icons and share image (`BRAND_PUBLIC_PATHS`) pass without the cookie, exact paths only.
- `sync/` progress across the family's devices (rules: `docs/spec.md` 5.7). Docs: `schema.ts` (zod, versions, `migrateDoc`) for the family profile doc, one main doc per child (state only) and one history doc per child and month. Pure logic: `merge.ts` and `history.ts` (commutative, associative, idempotent merges; a lesson reset is a marker that hides older records when read, `visibleHistory`, and never rewrites an old month), `clamp.ts`, `hash.ts`. Dexie side: `local.ts` and `local-history.ts` (records to docs and apply-back in one transaction), `dirty.ts` (a doc is sent when its hash differs from the one in `syncState`; no Dexie hooks), `policy.ts` (every table classified as synced or local). Client: `cycle.ts` (one doc: conditional GET, merge, conditional PUT, up to 3 rounds on 412), `engine.ts` (profile doc, months oldest first, main doc), `client.ts` (fetch wrapper), `scheduler.ts` (one run at a time, a debounce, a request during a run answered by one more run), `request.ts` (the app's engine, `requestSync`, the Web Locks lock `tutor-sync`: a run waits for it, the history pull skips a request while a sync holds it), `runner.tsx` (start, timer, online, page hidden; mounted in the child layout and the parent page), `history-pull.ts` (a new device pulls old months in the background, paced), and for the parent page `status.ts`, `family-switch.ts`, `import.ts`. Server: `server.ts` (`createSyncService`: cookie family, origin, size caps, schema, child listed in the profile doc, time clamp, `shrink` guard, daily snapshot of the main doc, rate limit, 412 with the stored doc; it never merges and never logs doc content). `store/`: the `BlobStore` contract (`types.ts`) with adapters `r2` (S3 API over `aws4fetch`, signed requests, no built-in retries), `fs` (a folder, local runs and the multi-device E2E) and `memory` (tests); `keys.ts` is the only key builder (`prod/` only when `VERCEL_ENV=production`, else `dev/`; `test/<run-id>/` for the optional real-bucket smoke) and `config.ts` picks the store from the environment: the four `R2_*` variables, or `SYNC_STORE=fs:<folder>` / `memory` outside production; none set means sync is off and the app behaves as it did before sync.
- `offline/` the service worker and everything around it (rules and numbers: `docs/spec.md` 5.9; the runbook to remove a bad worker: `docs/operations.md`). Build side: `routes.ts` (the pages' `generateStaticParams` call its param functions, `appPagePaths()` lists every static page, `NOT_PRECACHED_ROUTES` the ones left out; a test fails for a `page.tsx` in neither), `precache.ts` (pure: the entries the worker stores with their revisions, the deny list, the budget; no Node imports) and `precache-node.ts` (reads `public/` and the emitted content and hashes them), written by `scripts/offline-manifest.ts` to the gitignored `precache-list.generated.json`. `scripts/offline-worker.ts` runs after `next build`: it adds every `_next/static` file except ttf and woff and bundles `sw.ts` with esbuild into the gitignored `public/sw.js` (served at the root with `no-cache`, and public in `access/gate.ts`), failing above `PRECACHE_BUDGET_BYTES` or when the bundle reads `process.env`. Worker side: `strategy.ts` (pure `routeFor`, `fetchInit`, `storable`, `parseRange`, the flight entry names), `sw-core.ts` (install into one cache `offline-<buildId>` written all or nothing and copied from the previous build for unchanged entries, each page stored twice: its HTML and its RSC payload, the "flight" fetched with `RSC: 1` at `<page>?_rsc`; activation that deletes other builds' caches; network-first answers for pages (3 s, a page not stored gets `/offline` on a network error), the router's non-prefetch RSC fetches (3 s, then the page's stored flight as `text/x-component`, so an offline tap stays in the document) and lesson files (10 s) with the precache as fallback; precache-first for build files and sounds, a 206 slice for a `Range` request to a stored file; everything else, prefetches included, left to the browser; nothing is ever stored while answering), `sw.ts` (wires it to the worker's events), `config.ts` (path, cache prefix, messages, update timings). Page side: `register.tsx` (`OfflineManager`, mounted by the child layout and the parent screen, never on `/unlock`) over `update-controller.ts` (production only, in dev it unregisters; a new worker waits and takes over at boot, on the banner `components/update-banner.tsx`, or after the device was away 15 minutes, never inside a lesson player; after a failed install it waits 1 h, 6 h, then 24 h before the next attempt, kept in `localStorage`), `status.ts` and `components/parent/offline-status.tsx` (the parent line "Dùng khi không có mạng"). `flags.ts` holds the two build-time switches: offline support is off unless `NEXT_PUBLIC_OFFLINE_ENABLED=1`, and `NEXT_PUBLIC_OFFLINE_KILL_SWITCH=1` turns it off even then. When it is off the page registers nothing and unregisters any worker it finds, the parent line says "chưa bật", and the build writes `sw-kill.ts` (over `kill-switch.ts`) as the script: a worker that deletes the caches and unregisters. Only the offline lab and its E2E build with it on.
- `lib/brand.ts` is the one place for how the app presents itself outside its screens: names, colours, `SITE_URL` (also `PROD_URL` of `scripts/lib/release-config.ts`), icon list, share-card text and the public paths. `app/manifest.ts` serves `/manifest.webmanifest` (installable, standalone, `start_url` `/`; the manifest names no worker: `offline/register.tsx` registers it), the root layout carries the iOS tags, favicon links and Open Graph/Twitter tags (set there so `/unlock`, which a cookie-less crawler is redirected to, has them). Images are drawn by `pnpm brand:images` (`scripts/brand-images.ts`, `scripts/lib/brand-art.ts`) from `assets/brand/owl.svg` into `public/brand/` and `src/app/favicon.ico`, all committed.
- Grades: a series in `content/subjects.json` has a `grade` (1 to 12) and a lesson's grade is its series' grade; `content/grades.ts` holds the lookups (series of a grade, subjects of a grade, `openGrades` = grades with a published lesson). A profile stores `grade` (Dexie version 2 sets 6 on older profiles); `progress/summary.ts` `lessonsForSubject` resolves a child's series for their grade. Nothing lists locked subjects or grades by hand: a subject without a published lesson in the grade is a locked tile (`subject-tile.tsx`), a grade without one is locked on `app/(child)/grades/` and in the profile form.
- Visible grades: `VISIBLE_GRADES` in `lib/config.ts` (with `DEFAULT_GRADE` among them) is the only list of grades a screen shows; with one entry the profile form asks no grade and home has no grade chip, and a profile with no grade or a hidden one studies `DEFAULT_GRADE` (`learnerGrade` in `content/grades.ts`; the stored grade and its routes stay). To show a grade, add it to the list.
- Hidden subjects: `"visible": false` on a subject in `content/subjects.json` (absent = visible) leaves it and its lessons out of every list a child or parent sees (home tiles, "Học tiếp", stickers, parent report; `content/visibility.ts`); its routes and content stay. To show a subject, delete that line and rebuild. A single visible subject gets one full-width tile (`subjectTileLayout`).
- `components/` shared UI; `subject-style.ts` maps a subject's colour token and icon name to classes and components.

| E2E | `pnpm test:e2e` (`e2e/`) | `ipad` and `phone` targets in `e2e/targets.ts` |

Text fields the walker does not know fail `[fields]` until classified in `lint/walk.ts`.

## Media pipeline

- `video/`: `pnpm video:build <lesson> <name>` reads `video/projects/<lesson>/<name>/script.json` and `index.html` (HyperFrames), narrates each sentence (local VieNeu voice, checked against Whisper, slowed), lays karaoke subtitles, renders H.264, writes `public/media/video/<lesson>/` and `videos[]` in `lesson.json`. `pnpm narration:build <lesson>` (its `overview.narration` entry is excluded from the review hash, so rebuilding audio never invalidates a review) does the same for the lesson overview into `public/media/narration/`, but reads it with Gemini TTS: the whole overview in one request, cut into sentences at the pauses of Whisper's word times, each sentence still checked against the text (re-spoken one by one, same voice, when it fails).
- One voice per lesson: `video/projects/<lesson>/media.json` names it. `video/voices.ts` is the single catalog: each lesson voice maps to a `video` voice (local VieNeu preset) and a `narration` voice (Gemini preset of the same gender, from `GEMINI_NARRATORS`, one line per gender). Videos use the first, the overview narration the second; `script.json` has no voice. A narration or a video is read by one engine from start to end: if every Gemini key is out of quota, `narration:build` discards the Gemini sentences and reads the whole narration with the `video` voice, warns, and records the voice that read it in `overview.narration.voice` (`video:check` accepts only the lesson's two voices).
- Gemini keys: every `~/.config/gemini/api_key*` file (or `GEMINI_API_KEY`), used in turn per request by the one client `video/tts/gemini.ts` (also used by `pnpm sounds:build`); a rate-limited key rests while the others serve. Keys are never in the repo. Rules for choosing it and for the opening line of each video: skill `lesson-video`.
- TTS and Whisper run in the arm64 Python env `video/.venv` with models in `video/.hf` (setup: `video/requirements.txt`; paths in `video/config.ts`).
- Caches: sentence takes in `video/projects/**/audio/` and `video/.cache/`, intermediates in `renders/`; none is in git. `pnpm clean` removes the regenerable parts.
- `public/media/` (video, narration) is gitignored and uploaded per lesson to the media bucket with `pnpm media:upload` (`NEXT_PUBLIC_MEDIA_BASE_URL`, read at build time and checked by `next.config.ts`, switches the client to it through `mediaUrl`). `pnpm deploy:prod` ships the committed `HEAD` from a clean temporary worktree and smoke-checks production; targets (bucket, project, URL, content types) live in `scripts/lib/release-config.ts`, tests in `tests/scripts/media-upload.test.ts` and `tests/scripts/deploy-prod.test.ts`. Both commands write outside the machine and run only with the owner's approval; the release order (publish, media, upload, deploy, smoke test) is in `docs/operations.md`. `public/sounds/` (shared app sounds, `pnpm sounds:build`) is committed and served with a one-year immutable cache (a clip's URL carries its hash in `?v=`; `CACHE_HEADERS` in `next.config.ts`, which also gives `/content/*` 60 seconds plus background revalidation; the family-code gate sets no cache headers of its own); clips imported from other files (`file` entries: correct answer, wrong answer, finish, the sticker celebrations, leaving, the sticker sheet's songs, the background music, the recorded avatar effects) are made from `assets/sounds/`, also committed; a clip peaking too sharply to reach the voice loudness under the peak ceiling is brought there with a brief limiter (`master` in `scripts/lib/tone-render.ts`). Profile avatars and the owl's tap each have a clip: `AVATAR_CLIP_IDS` (`src/lib/sound-manifest.ts`) maps avatar id to clip id, a recorded effect is a `FILES` entry with its source and licence, an animal without one is a spoken onomatopoeia in `AVATAR_LINES` (`src/mascot/lines.ts`).

## Content authoring pipeline

`import-source` (PDF pages to `sources/`) then `lesson-author` (lesson.json with overview, tips and an explanation per exercise; calls `lesson-visual` for figures, runs `lesson:walk`) then `lesson-review` (fresh subagent; writes `review.md`, sets `reviewedHash`, publishes; then `pnpm content:lock <lesson>` locks that lesson's ids and only those) then `lesson-author` again for `lesson-video` and narration. A published lesson gains tips without a new lesson review: `tips.json` beside `lesson.json`, reviewed on its own (`lesson-review`, `pnpm content:hash <lesson> --tips --approve`). Skills live in `.claude/skills/`; which model runs each step is in `.claude/rules/agents.md`. Recurring review errors go to `docs/lessons-learned/`, which author and reviewer read first.

## Conventions

Kept in `.claude/rules/` so each is stated once: `content.md` (ids, rule and guide markers, review hash, textbook copying, review lessons and book-practice sections), `video.md` (verbatim quotes, caches, shared sounds), `agents.md` (model choice, handovers, external writes, commit hygiene).

## Where state lives

- `notebooks/backlogs/index.md`: lesson status table, ordered queue, open follow-ups; each item links to its backlog folder. `notebooks/backlogs/<name>/{spec,plan,task}.md`: planning docs of one feature, bug or lesson (only the files it needs); for a lesson, `task.md` is the handover while in progress and the non-blocking leftovers after publishing. `notebooks/backlogs/archive/`: finished backlog folders.
- `docs/learner.md`: the learner profile. `content/ids.lock.json`: published ids. Child progress: IndexedDB in the browser, and, when `R2_*` are set, the synced docs in the private `tutor-progress` bucket (`sync/`).
- Secrets: none in the repo; `.env*` is gitignored, `.env.example` documents names (`FAMILY_CODE_SECRET`, `FAMILY_CODES_REVOKED`, `SESSION_SECRET`, `NEXT_PUBLIC_MEDIA_BASE_URL`, `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_PRIVATE_BUCKET`). Where each is set in production and every external step to deploy: `docs/operations.md`.
